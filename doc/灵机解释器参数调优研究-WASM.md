# 灵机解释器参数调优研究（WASM-GUI 目标）

范围：`infer/vendor/Animac`（amalgam 形态，基线 `5f82267`）中与**时间片长度**、**GC 周期**、
**GC 策略**相关的可调宏，在 **WASM-GUI 目标**（`infer/build_wasm_gui.sh` → `infer/webgui/`，
不是 `infer/web/` 那条 LLM-only 路线）下、针对 `infer/app/` 现有的 39 个灵机应用，
在**内存波动平稳**的前提下尽量提升性能。

结论先给：**只改两个 GC 宏**（高水位 0.75→0.65、兜底周期 32→16 帧），
时间片与其余 GC 策略参数**保持现状**。收益：39 App 平均堆峰值 −23%、最坏峰值 −14%、
单次 GC 平均停顿普遍 −20%~−50%、长跑最大停顿全部下降，代价是 GC 占用 CPU 从 1.68% → 2.31%
（+0.63 个百分点），浏览器端 fps 与呈现序列完全不回归。

## 0. TL;DR（推荐配置）

| 参数 | 现状 | 建议 | 效果 |
|---|---|---|---|
| `AM_GC_HEAP_HIGH_WATER_RATIO` | 0.75（= 12MB） | **0.65**（= 10.4MB） | 堆峰值从贴 12MB 降到 ≤10.4MB，给 16MB 硬上限留出余量 |
| `AM_GC_HEAP_CRITICAL_RATIO` | 0.90（= 14.4MB） | **0.80**（= 13.4MB） | 随高水位等比下移，保留"临界强制压缩"这层保险 |
| `AM_GC_PERIODIC_INTERVAL` | 32 轮（≈32 帧≈0.5s） | **16 轮（≈0.27s）** | 单次 GC 看到的垃圾减半 → 平均停顿减半、峰值大幅下降 |
| `AM_HEAP_COMPACT_INTERVAL` | 1（每轮都压缩） | **保持 1** | 实测每轮压缩**反而最快**（碎片会让后续标记变慢），且运行期堆无法扩界，不压缩会 OOM |
| `AM_GC_WATERMARK_CHECK_STRIDE` | 256 条指令 | **保持 256** | 256/2048/4096 实测无可测差异；256 的失控分配逃逸窗口最小 |
| `AM_GC_HEAP_FRAG_*` | 0.30 / 0.03125 | **保持** | 未发现误触发，也没有可测代价 |
| `MB_TIMESLICE_TICKS`（宿主，非解释器） | 312500 | **保持 312500** | WASM 下实测 22–23ns/指令 → 最重 App 每帧 7.2ms ≈ 60Hz 预算的 44%，给慢设备留 2x 余量 |
| 内存池（宿主） | 32MB（= 16MB VM + 16MB 堆） | **保持** | `markdown` 编译期 VM 需求决定下限；运行期堆上限无法扩界，故堆 16MB 是硬上限 |

落地方式（`infer/build_wasm_gui.sh`，解释器核心支持 `#ifndef` 覆盖，**不需要改 vendor 源码**）：

```diff
-"$EMCC" -O3 -ffast-math -DNANO_WASM_GUI \
+"$EMCC" -O3 -ffast-math -DNANO_WASM_GUI \
+    -DAM_GC_HEAP_HIGH_WATER_RATIO=0.65 \
+    -DAM_GC_HEAP_CRITICAL_RATIO=0.80 \
+    -DAM_GC_PERIODIC_INTERVAL=16 \
```

（`AM_*` 宏在 `animac_core.h` 里都是 `#ifndef` 保护的默认值，命令行 `-D` 即生效，
产物里不留下任何对上游源码的改动。）

## 1. 参数清单：它们到底在什么时候起作用

先把"纸面参数"翻译成 WASM 目标上的**实际行为**，否则调参很容易调在没被走到的分支上。

### 1.1 时间片（这里是宿主的参数，不是解释器的）

`infer/ui_scheme_app.c`：`MB_TIMESLICE_TICKS = 312500`；每帧（`main_wasm_gui.c` 的
`wasm_gui_frame`，rAF 节奏）调用一次 `am_runtime_event_handler(rt)`，其中
`am_runtime_tick(rt, rt->timeslice)` 最多执行 312500 条 IL 指令。

- `AM_COMPUTATION_PHASE_LENGTH = 1` → 每个事件循环轮 = 1 个 tick = 最多 1 个时间片。
- 时间片**不决定总吞吐**（CPU 饱和时总指令数恒定），它决定**单帧最多推进多少**：
  自定拍 App（`System.set_interval`）在定时器没到期时 tick 立即 IDLE、不消耗时间片；
  "能算多算"的 App（pathtracer / mandelbrot / flip / mlp）则被打满 → 时间片直接决定
  这类 App 的**每帧推进量**。

### 1.2 "堆水位"比例是相对**堆区容量**，不是相对池

`am_allocator_pool_create()` 把池 **50/50** 切开：`boundary = total/2`。
WASM 池 32MB → **堆区 16MB、VM 区 16MB**，且运行期**无法再调整边界**：

> `am_allocator_pool_adjust_boundary()` 明确要求"堆扩张时 VM 工作区必须为空"，
> 而运行期 VM 区永远非空 → 堆上限被钉死在 16MB。

所以 `AM_GC_HEAP_HIGH_WATER_RATIO = 0.75` 的真实含义是"**堆用到 12MB 就回收**"，
`CRITICAL = 0.90` 是"14.4MB 强制压缩"。这也解释了为什么改这个参数是本轮最有效的旋钮：
它其实是唯一能设置**堆占用绝对上限**的旋钮。

（同一份参数换到 ESP32 目标（池 2MB → 堆 1MB）语义一致，只是绝对上限等比缩小。）

### 1.3 GC 的两级触发

```c
am_runtime_tick()             // 每个时间片
    while (timeslice--) {
        执行 1 条指令;
        if (++since_check >= AM_GC_WATERMARK_CHECK_STRIDE)   // 每 256 条
            runtime_gc_watermark_check();                    // L1：按堆水位
    }
    runtime_gc_watermark_check();                            // 时间片末尾（= 帧末尾）
am_runtime_event_handler()
    每 AM_GC_PERIODIC_INTERVAL 轮 → am_gc_collect()           // L2：周期兜底
```

- **L1（水位）**：堆占用 ≥ 75% 就标记-清除；≥ 90%（或发生过分配失败）当轮强制压缩。
  粒度是 256 条指令，所以水位是"**帧内**也能触发"的，峰值过冲很小。
- **L2（周期）**：每 32 轮无条件回收一次。多数 App（堆占用 < 12MB）**只走 L2**，
  所以 `AM_GC_PERIODIC_INTERVAL` 实际决定了绝大多数 App 的**垃圾累积量**——
  也就同时决定了"堆峰值的锯齿幅度"和"单次停顿长度"。

### 1.4 GC 的成本结构（这条决定了后面所有取舍）

`am_gc_process()` 每轮做三件 O(N) 的事，N = **堆把柄表长度**（不是活跃字节数）：

1. 扫全表找 keepalive 对象（`am_map_keys()` + 每把柄一次 `am_heap_get()`）；
2. 从 GC 根递归标记（成本 = 活跃对象图）；
3. `gc_sweep()` 再扫全表、逐把柄判活并释放（又一遍 `am_map_keys()` + `am_heap_get()`）。

实测印证：`mandelbrot` 稳态活跃堆只有 30KB，但每轮 GC 要扫 **16.7k 个把柄**（全是垃圾），
单轮 1.4ms（宿主）/ ≈5ms（浏览器）；`2048` 只有 1.5k 把柄，单轮 0.14ms。二者差 10 倍，
与"活跃字节数"完全无关。

由此得到一条重要的**反直觉**结论：

> 把 GC 做得更频繁，**总扫描量并不会同比例增加**（垃圾还没长大就被收掉），
> 而**单次停顿会成比例下降**。实测 39 App × 600 帧的总扫描把柄数：
> 周期 32 → 4.51M，周期 16 → 5.85M（+30%），周期 8 → 8.41M（+87%）。
> 周期 16 只付 +30% 的扫描量，就换来一半的停顿和大幅下降的峰值。

## 2. 测量方法（可复现）

三个计测台，都不改产品代码：

1. **宿主确定性计测台**（主力）：`infer/tools/e2e/host/harness.c` 的同源变体，
   真实 `graphics.c` + 真实本地库 + 虚拟时钟（每帧 +16ms）→ App 行为完全可复现。
   逐帧记录 `heap_used / heap_capacity / vm_used / rt->gc_count`、帧耗时，
   并用 `getrusage(RUSAGE_SELF)` 取**进程 CPU 时间**（墙钟受本机负载影响 ±30%，
   CPU 时间稳定得多）。
2. **GC 内部计测**：在 `/tmp` 里的 vendor **副本**上加 `AM_BENCH_GC`
   （`am_gc_collect` / `am_gc_process` 内分段时间、把柄表长度、水位级别计数），
   产品目录里的 vendor 保持上游原样。注意：WASM 下 `CLOCK_THREAD_CPUTIME_ID`
   不工作（返回 0），浏览器构建必须用 `CLOCK_MONOTONIC`/`emscripten_get_now()`。
3. **真 WASM + 真无头浏览器**：`emcc` 构建带 `wasm_bench_stat()` / `wasm_frame_stat()`
   导出的测量版，Chromium（playwright）逐 App 采样，量 GC 次数/时间/最大停顿/帧耗时/
   fps。**同一 App 的变体必须交替重复**（本机 load average ≈10，单跑差异可达 ±30%）。

**不变量**（用来证明"调参没改语义"）：

- 宿主台：39 App 的 `refresh` 计数在基线与候选配置下**逐项相等**；整帧 CRC 也相等，
  唯一例外是 `xray`（它把 GC 计数/活对象数画在屏幕上，CRC 必然变）→ 见 §5.1。
- 浏览器：用产品构建脚本各编一份产物跑 `regress_det.js`，37 App 的
  `launch/end state`、`refreshΔ`、`crc` 逐项相等，唯一例外是 `forkqueue`
  （同样显示 `Diag.heap` 活对象数，且它在**同一份产物上**连跑两次 CRC 都不同）。
- 长跑 2000 帧：`oom=0`、`level2 GC=0`、`err=none`。

  半帧的停顿，是 WASM 目标上唯一能被人眼看见的 GC 代价。

## 4. 逐个参数的实验结果

### 4.1 `AM_GC_PERIODIC_INTERVAL`（周期兜底）：32 → 16 是甜点，8 太贵

39 App × 600 帧（宿主，min-of-2）：

| 配置 | GC 次数 | GC CPU | GC 占比 | 堆峰值均值 | 最坏峰值 | 最大停顿 |
|---|---|---|---|---|---|---|
| 32（现状） | 762 | 422.9ms | 1.68% | 4796K | 12272K | 3.62ms |
| **16** | 1476 | 580.9ms | **2.31%** | **3687K（−23%）** | **10594K（−14%）** | 3.62ms |
| 8 | 2932 | 1075ms | 3.05% | 2993K（−38%） | 11924K | 6.5ms |

> 注意 8 档的"最大停顿"反而变大：结果是 39 App 全体 GC 的最大值，采样数翻倍后
> 更容易撞到异常点。看**每 App 的平均停顿**才是稳定口径（见下表）。

每 App 平均停顿（周期 32 → 16，节选）：

| App | 平均停顿 | 堆峰值 |
|---|---|---|
| mlp | 1.89ms → **0.91ms** | 8.8MB → 4.4MB |
| xray | 1.48ms → **0.99ms** | 10.0MB → 8.4MB |
| gol | 2.08ms → **1.48ms** | 11.4MB → 9.8MB |
| maze3d | 1.11ms → **0.64ms** | 6.5MB → 3.3MB |
| mandelbrot | 0.93ms → **0.57ms** | 12.0MB → 10.4MB |
| fallingsand | 1.11ms → **0.85ms** | 12.0MB → 10.1MB |
| sky3 | 0.62ms → **0.46ms** | 11.0MB → 5.6MB |
| pathtracer | 0.40ms → 0.36ms | 11.7MB → 6.4MB |
| markdown | 1.64ms → 1.55ms | 7.8MB → 7.5MB |

代价侧（小幅回退）：轻量 App 的总 GC 时间翻倍（`2048` 2.5→4.3ms、`calculator` 4.2→7.9ms、
`notepad` 0.8→1.3ms 每 600 帧），因为它们每次 GC 的固定开销（建 2048 槽根表、
扫活跃集、压缩）占了主导；`markdown`（大活跃集 + 几乎不分配）GC 时间 29.6→57.4ms，
是唯一明显变差的 App。

**取舍**：+0.63pp CPU 换 −23% 峰值、平均停顿减半。周期 8 再多付 0.7pp 却几乎不再改善
最坏峰值（受限于几个 App 的**瞬时活跃集**，见 4.2），不推荐。

> 注意 `markdown` 这一档是"翻倍"而不是"减半"：它是**大活跃集 + 几乎不分配**的极端，
> 每轮 GC 的固定成本（扫 11k 把柄、压缩 1.1MB 活跃对象）占主导，付了频率却没省下扫描量。
> 它也是全场唯一"GC 占比没变好"的 App（11% → 约 20%）；但因为它的总 CPU 只有
> 263ms/600 帧，绝对增量 ≈28ms，可接受。

### 4.2 `AM_GC_HEAP_HIGH_WATER_RATIO`（水位）：只能降一点，降多了会 GC 风暴

水位是"帧内"也能触发的（每 256 条指令查一次），所以它能真正把峰值钉住；
但如果**水位低于某个 App 的瞬时活跃集**，就会出现"回收完仍然超标 → 下 256 条指令又回收"
的活锁。实测（重负载子集 × 600 帧）：

| 高水位 | 相当于 | 典型现象 |
|---|---|---|
| 0.75（现状） | 12.0MB | 正常 |
| 0.65 | 10.4MB | 正常，峰值 −14%，`xray` 峰值 8.4MB < 上限，无错误 |
| 0.50 | 8.0MB | **`xray` GC 次数 18 → 746**，GC CPU 27ms → 1017ms（+37 倍） |
| 0.25 | 4.0MB | **`xray` GC 次数 18 → 41,969**，GC CPU 44.8s，占运行时间 66%；`hwr2` 也中招（2,836 次） |

根因（值得记住）：**水位是按"堆已用"判的，而已用包含"瞬时活跃集"**。
`xray` 每帧会构造一个约 **8.5MB 的临时大列表**（显示用），这段窗口里"已用"必然超标；
水位一旦低于 8.5MB，回收就变成每个检查点都触发一次。
实测"GC 时刻观察到的最大活跃集"= **8.58MB**（xray），`hwr2` 的常驻活跃集 = **5.01MB**。

所以高水位的**安全下限**是 ≈10MB（比例 0.62），取 **0.65（10.4MB）**留 20% 余量。
这也说明：**不要试图用水位把峰值压到 5MB 以下**——那是活跃集的地板，压不动。

### 4.3 `AM_HEAP_COMPACT_INTERVAL`（压缩频率）：1 就是最优，且不能关

直觉是"少压缩省时间"，实测相反（7 个重负载 App × 600 帧，min-of-3 CPU 时钟）：

| 压缩间隔 | GC 总数 | GC CPU | 其中扫表 | 其中压缩 | 堆峰值 |
|---|---|---|---|---|---|
| **1（现状）** | 145 | **200.6ms** | 150.2ms | 50.4ms | 7.1MB |
| 2 | 145 | 235.0ms | 208.1ms | 26.8ms | 9.1MB |
| 4 | 148 | 205.5ms | 192.0ms | 13.5ms | 7.1MB |

压缩时间确实省了一半，但**标记/清除变慢了更多**：不压缩时活跃对象散落在 12MB 里，
两趟 O(N) 扫表的缓存局部性变差。净结果是每轮都压缩最快，而且峰值最低。

更关键的是**正确性**：堆上限固定、运行期不能扩界，长期不压缩会碎到分配失败。
1200 帧长跑下 `AM_HEAP_COMPACT_INTERVAL=4` 与 `=0` 都让 `xray`
**直接 `[Runtime] 指令执行异常`**（refresh 从 299 掉到 76/44，`err` 置位），
而 `=1`/`=2` 正常。**结论：保持 1。**

### 4.4 `AM_GC_WATERMARK_CHECK_STRIDE`（水位检查步长）：无影响

256 / 2048 / 4096 三档，39 App 的 GC 次数、GC CPU、峰值全落在噪声内
（`am_gc_heap_watermark_level()` 第一趟是 O(1) 读两个计数，第二趟碎片检查只在
已用 ≥30% 时才走）。保留 256：非零收益没有，但它把"失控分配"的逃逸窗口压到最小。

### 4.5 时间片 `MB_TIMESLICE_TICKS` = 312500：现在这个值是对的

真 WASM（Chromium 无头，本机）实测：`pathtracer` 在 312500 下每帧 7.32ms、
625000 下 13.73ms → **≈22–23ns/指令**（与宿主 x86 的 20.7ns 基本一致，
说明这套参数在 wasm 与原生之间可以互相换算）。

| 时间片 | `pathtracer` 每帧耗时 | 占 60Hz 预算 | >16.7ms 的帧（4s） | 说明 |
|---|---|---|---|---|
| 156250 | 4.40ms | 26% | 0 | 有余量，但逐帧推进量腰斩 |
| **312500（现状）** | **7.32ms** | **44%** | **0** | 给慢设备留 2x 余量 |
| 625000 | 13.73ms | 82% | 6（pathtracer）/3（flip）/6（sky3）/7（gol） | 开始掉帧，不推荐 |
| （450000，推算） | ~10.3ms | ~62% | — | 按 22–23ns/指令线性外推；实测那一轮赶上机器负载异常，数据不干净，故不采信 |

- 时间片**不影响**自定拍 App（`set_interval` 未到期时 tick 立刻 IDLE，不吃时间片），
  只影响"能算多算"的 App：实测 `pathtracer` 的每秒推进量 7.4 → 14.9（×2.0）、
  `flip` 14.9 → 21.2，`flip`/`pathtracer` 的每帧时耗同比例上升。
- 顺带：`fallingsand` 在**任何**时间片下都有 7~11 帧 >16.7ms —— 那不是时间片的锅，
  是它自己"一次性生成关卡 + 大瞬态"导致的 GC 停顿；这正是 §0 的配置要解决的问题
  （浏览器实测 `mandelbrot` 的 >16.7ms 帧 7 → 1）。
- 峰值内存基本不受时间片影响（帧内的水位检查会兜住），所以"调大时间片"不会破坏
  内存平稳性，风险只在掉帧。
- 结论：**312500 保留**。只有确认目标设备全是桌面级浏览器时，才考虑 450000。

（我试过"帧预算自适应时间片"（按上一帧耗时 PID 调 `rt->timeslice`，目标 6/9/12ms）：
在无头 Chromium 上**抖动明显**（`flip` 出现 72~81 帧 >16.7ms，`mlp` 27.9fps @ 6ms 目标，
比固定 312500 还差），原因是单帧耗时方差大 + 每帧 2x 的增长步长过冲。
要做得稳需要中位数滤波 + 更小的增长步长，属于后续工作，本轮不建议上线。）

### 4.6 内存池大小与切分：不动

- 池 32MB 是 `markdown.scm`（连 `md_parse`/`md_layout`/`md_demo`/`exit`/`filepicker`/`fsx`
  一起编译）**编译期 VM 区**的需求决定的：24MB 时编译期就 OOM。
- 池 50/50 切分 + 运行期不能扩界 → 堆 16MB 硬上限。想改"堆上限"只有两条路：
  改池大小，或改高水位比例。本轮选了后者（不动内存总量，只动回收时机）。
- 若将来把池提到 40MB（堆 20MB），**必须同步把高水位比例除以 1.25**（0.65 → 0.52），
  否则绝对上限会从 10.4MB 变成 13MB，等于白调。

## 6. 结论与理由（为什么是这两个参数，而不是别的）

1. **GC 的成本由"每轮看到的把柄数"决定，不由活跃字节决定**。所以：
   - 提高频率（周期 32→16）→ 每轮看到的垃圾减半 → 停顿减半、峰值大降，
     而总扫描量只增加 30%（因为垃圾没长大就被收掉）。
   - 压缩频率降低只会把成本从"压缩"搬到"标记/清除"（碎片伤局部性），
     还会在长跑里直接 OOM，**故保持每轮压缩**。
2. **水位比例是唯一能设置"堆绝对上限"的旋钮**（因为运行期堆无法扩界），
   但它有硬下限：不能低于 App 的瞬时活跃集（实测 8.58MB），否则 GC 风暴。
   0.65（10.4MB）是"低于 12MB 现状、又高于 8.6MB 地板"的唯一安全区间。
3. **时间片已经是按 60Hz 帧预算标定过的**（最重 App 占 44%），在 WASM 上
   22–23ns/指令与原生一致；它的作用是"每帧推进量上限"，不是吞吐，因此
   **提升性能的重心不在它身上**，动了只会拿掉慢设备的余量。
4. 内存"波动平稳"的真正含义在本项目里有两层：
   - **锯齿幅度**（峰值−谷值）：由"两轮 GC 之间累积的垃圾"决定 → 周期参数管；
   - **峰值余量**（相对 16MB 硬上限）：由水位参数管。
   两个参数正好各管一层，所以是"水位 0.65 + 周期 16"的组合，而不是单改一个。

## 7. 风险、边界与回退

- **回退**：删掉 `build_wasm_gui.sh` 里那三行 `-D` 即回到现状；不涉及 vendor 源码、
  不涉及 App 代码、不涉及渲染路径。
- **活跃集长大就危险**：高水位 10.4MB 的安全前提是"没有 App 的瞬时活跃集 > 10MB"。
  目前最坏是 `xray` 8.58MB（占 82%）。若将来出现更大的瞬态，请先用本报告的量法
  （`am_bench_live_max` / 逐帧 `heap_used` 峰值）复核，再决定是否抬回 0.75。
- **`markdown` 是唯一 GC 时间明显变差的 App**（29.6→57.4ms/600 帧，因为它是
  "大活跃集 + 几乎不分配"，每轮 GC 的固定成本占主导；GC 占自身 CPU 从 11% 升到约 20%）。
  如果以后觉得它卡，可考虑放宽它的周期（解释器参数是全局编译期宏，做不到按 App 调；
  除非宿主引入一个"GC 参数 setter"，属上游改造）。
- **WASM 下 GC 停顿是宿主端的 3~5 倍**（mandelbrot 单轮 1.4ms → ≈5ms），
  这是浏览器上唯一可见的 GC 影响。若后续还要进一步压停顿，路线是上游改算法
  （把 keepalive 扫描与 sweep 合并成**一趟** `am_heap_iter()` 遍历——两者本来都是在
  "遍历堆表全部把柄"，现在却各自 `am_map_keys()` 出一份 4~30 万个把柄的数组再做一次
  逐把柄 `am_heap_get()`；合并后可以省掉两次大数组分配和一遍哈希查找，
  按本轮数据估计能省 40%~50% 的扫表时间），而不是继续调参数。

```bash
# 1) 宿主确定性计测（虚拟时钟，逐 App 采 GC/内存/帧耗时）

```
